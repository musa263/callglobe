# Organizations and Access

`pbx.ts::listExtensions` loads the directory for an organization and resolves
the active engine's credential requirements. `createExtension`, `updateExtension`
and `deleteExtension` coordinate directory/credential changes. Tenant-sensitive
callers must supply the expected organization, not trust a client extension ID.

`tenancy.ts` resolves session ownership. `pbx-config-store.ts` reads company
settings and saves version-checked updates. `saas-store.ts` separates platform
catalog operations from `readTenantSaasState`; `effectiveEntitlements` combines
plan and feature overrides. `saas-access.ts` is the route-facing access gate.

`office-hours.ts` and `user-call-routing.ts` determine availability/destinations.
`routes/` exposes company users, PBX settings, SaaS controls and the voice directory.
Colocated tests cover tenant scope, role handling, hours and routing. Use frontend
`npm test` plus `npm run check:api`.

## Vocivo extension authority (migration stage 1)

`vocivo-extensions.ts` owns the carrier-independent directory lifecycle. An
encrypted v3 directory with `authority: vocivo` makes the `pbx.ts` facade use
local creation, lookup, updates, deletion and SIP username resolution. New IDs
and SIP usernames are generated by Vocivo. Device passwords are issued by the
existing SIP credential API; no permanent per-extension carrier password is
created. Request fields are allowlisted so login passwords and client-supplied
IDs cannot become directory fields. Slot allocation happens inside the directory
transaction; edits re-read the latest identity and never restore a deleted user.

Adoption keeps existing IDs, SIP usernames, tenant assignments, numbers, roles,
status and creation dates. It changes only the authority marker/provider label;
history and account links continue using the same IDs. Historical Telnyx
credential records remain archived and are never read by the Vocivo lifecycle.
Updates/deletions revoke extension sessions; SIP registration also checks the
current directory. Revocation failure prevents those mutations.

Missing/corrupt directories are different: missing legacy storage can bootstrap
through the old managed path, but corrupted/unknown-version storage fails closed.
The migration refuses a missing directory unless explicitly initializing an empty
installation. It validates unique IDs, globally unique SIP usernames and unique
extension numbers per tenant. Legacy writes carry an expected authority so an
in-flight old request cannot overwrite an adopted directory.

Run `node --import tsx scripts/migrate-extension-authority.mjs --env-file PATH`
from `frontend` for a dry-run; `--apply` adopts the stored directory. Application
and inbound SIP must both be selected before adoption. This is deployment work,
not performed by the test suite. See the [migration runbook](../../../../../docs/runbooks/vocivo-carrier-only-migration.md).
After adoption, changing the engine back to managed Telnyx fails closed. An older
binary without v3 support must not be deployed against this directory.

The regression suite exercises encrypted migration, no-network lifecycle,
concurrent slot allocation, cross-tenant denial, immutable identities, revocation
failure and deletion races. Real database migration, device login and SIP audio
remain deployment acceptance checks.

## Explicit admin tenant scope

After verifying authentication, tenant admin routes call
`request-organization.ts::requestOrganizationId`. Superadmins must send a single
`organizationId` query parameter. Company users default to their verified tenant
and cannot override it. Only the initial read-only PBX GET may choose the saved
default; no tenant mutation may do so. An old unscoped superadmin client fails
closed and must reload the current UI. Platform SaaS and wallet routes remain
separate from customer navigation.

`admin-pbx.ts` saves only the selected company's settings, organization record and
user profiles. The returned `workspaceVersion` guards the form's loaded revision;
the store's transactional `expectedUpdatedAt` guards changes during the request.
AI and business voice use their dedicated routes and are not overwritten by a
general PBX form. Workspace selection never changes global `activeOrganizationId`.
